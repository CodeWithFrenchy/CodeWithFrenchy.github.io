Aspire 17.0 est disponible depuis le 17 novembre 2026. Cette version réorganise le tableau de bord autour des ressources de l’application, enrichit le CLI et fait progresser la prise en charge de Go. Elle stabilise aussi le déploiement Kubernetes et plusieurs API, tout en apportant des changements qui peuvent demander une migration dans les projets existants.

Les [notes de version d’Aspire 17.0](https://aspire.dev/whats-new/aspire-17/) présentent les nouveautés et les consignes de mise à niveau. Les [notes publiées sur GitHub](https://github.com/microsoft/aspire/releases/tag/v17.0.0) résument également les changements incompatibles.

## Le tableau de bord met les ressources au premier plan

La page d’accueil du tableau de bord affiche maintenant les ressources dans un tableau pleine largeur. On peut les rechercher, les filtrer, en sélectionner plusieurs et les regrouper par étiquette, type ou état. Les détails d’une ressource rassemblent son état de santé, ses points de terminaison, ses journaux et ses données de télémétrie.

La vue All resources donne un aperçu de l’application : état des ressources, activité des requêtes, taux d’erreur, latence p95, points de terminaison les plus lents et ressources les plus sollicitées. Les traces distribuées permettent de suivre le temps passé dans chaque service et chaque dépendance. La page des métriques affiche les valeurs en cartes avec des graphiques actualisés en direct. On peut épingler les métriques consultées souvent.

Les terminaux interactifs ont maintenant leur propre page, séparée des journaux de console. Le graphe des ressources peut aussi être exporté en Mermaid depuis l’interface ou avec la commande suivante :

```bash
aspire describe --format mermaid
```

Cette exportation permet d’ajouter une représentation des dépendances de l’application à une demande de fusion ou à un document d’architecture. Le format Mermaid ne peut pas être combiné avec l’option `--follow`.

## Le CLI facilite le travail quotidien et la configuration d’équipe

Aspire 17 ajoute la complétion des commandes dans Bash, Fish, PowerShell et Zsh. Les secrets peuvent être associés à un environnement avec `aspire secret`. Le CLI peut demander leur valeur dans une invite masquée ou la lire à partir d’une variable d’environnement, ce qui évite de la placer directement dans la commande.

Les équipes peuvent aussi déclarer des sources personnalisées pour les modèles de projet, les intégrations d’hébergement et les extensions destinées aux agents de codage. La configuration peut être initialisée depuis un dépôt Git avec `ASPIRE_INIT_SOURCE_URL`. Aspire demande le consentement avant d’adopter cette configuration. Les modèles et les extensions peuvent contenir du code exécutable, donc il faut utiliser uniquement des sources de confiance.

La commande `aspire agent init` permet de choisir GitHub Copilot, Claude Code ou OpenCode, puis de configurer le périmètre du projet ou celui de l’utilisateur. Aspire configure le plug-in dans le mécanisme de marché de l’agent, au lieu de copier un dossier de fichiers d’instructions dans le dépôt.

Un compagnon de barre d’état est également disponible en aperçu. Il affiche les AppHost locaux dans la barre de menus de macOS, la zone de notification de Windows ou un environnement Linux compatible. Il requiert une installation native du CLI. Sous Linux, il faut aussi une session graphique et GTK 3.

## Go entre dans les AppHost en aperçu

Aspire permet maintenant de créer un AppHost en Go sans activer de drapeau expérimental. Les modèles `aspire-go-empty` et `aspire-go-starter` sont disponibles dans `aspire new`. Le modèle de démarrage comprend une API Go, une interface React et Redis.

La prise en charge demeure en aperçu. L’extension Aspire pour Visual Studio Code peut lancer et déboguer un AppHost Go avec l’extension Go et Delve, et s’attacher aux ressources Go et .NET déjà en cours d’exécution. `aspire doctor` vérifie notamment la présence de Go 1.26 ou d’une version ultérieure. Le SDK Go généré peut être exporté avec `aspire sdk export --language go`.

L’extension Visual Studio Code apporte aussi des outils de modèle de langage pour consulter l’état d’une session de débogage, trouver les AppHost lancés par VS Code, comprendre un échec de démarrage, vérifier si Hot Reload s’applique et ouvrir le tableau de bord. Ces outils retournent un état résumé plutôt que des journaux bruts, des variables d’environnement ou des URL de connexion au tableau de bord.

## Les changements d’AppHost modernisent l’intégration des projets

Aspire 17 relève à .NET 10 la version minimale prise en charge par l’AppHost. Cela ne signifie pas que toutes les applications orchestrées doivent cibler .NET 10. Il faut toutefois vérifier le framework cible du projet AppHost avant la mise à niveau.

L’intégration `Aspire.Hosting.Dotnet` est maintenant stable et favorise l’enregistrement des projets à partir de leur chemin avec `AddDotnetProject`. Les anciennes API `AddProject` restent présentes, mais elles sont dépréciées. `Aspire.AppHost.Sdk` est également obsolète et déclenche l’avertissement ASPIRE012. Les nouveaux AppHost C# utilisent `Microsoft.NET.Sdk` et des références de packages explicites. Aspire 17 ne migre pas automatiquement les projets qui utilisent encore l’ancien SDK.

Les paramètres peuvent être déclarés facultatifs avec `AsOptional()`. Lorsqu’un paramètre facultatif n’a pas de valeur, il devient `null` et Aspire ne demande pas de valeur pendant `aspire run`. Un paramètre obligatoire vide n’est plus accepté. Il faut donc garder les secrets et les autres valeurs requises obligatoires, et ne rendre facultatifs que les paramètres dont l’absence est valide.

Les nouvelles références `PrimaryBrowserOrigin` et `BrowserOrigins` aident à configurer CORS et les redirections d’authentification sans coder les URL en dur. Elles tiennent compte des domaines `*.dev.localhost`, des URL publiques et du transfert de ports dans GitHub Codespaces.

Plusieurs API ne signalent plus leur statut expérimental, notamment des fonctions de pipeline et de déploiement, les sondes HTTP, Deno, Next.js et les points de terminaison MCP. Après la mise à niveau, les suppressions de diagnostics expérimentaux devenus stables peuvent permettre de retirer les avertissements correspondants de `.editorconfig`, des fichiers projet et des directives `#pragma`.

## De nouvelles intégrations Azure et IA

L’intégration Microsoft Entra ID, en aperçu, permet de modéliser des inscriptions d’applications et des principaux de service dans l’AppHost, ou de référencer des inscriptions gérées ailleurs. Elle fournit la configuration d’identité aux charges de travail, mais n’ajoute pas le middleware d’authentification et ne protège pas les routes de l’application. Cette configuration reste à faire dans l’application consommatrice.

L’intégration Azure API Management, elle aussi en aperçu, permet de décrire une passerelle, ses API, ses backends et ses politiques, puis d’importer des documents OpenAPI. API Management est une ressource de déploiement. Elle n’est pas créée lors de `aspire run`, et les services locaux peuvent continuer à fonctionner sans passerelle.

Les packages Aspire pour Azure OpenAI et Microsoft Foundry s’alignent sur le SDK OpenAI standard. `Aspire.Azure.AI.Extensions.OpenAI` enregistre un `OpenAIClient`. `Aspire.Azure.AI.Projects` enregistre un `AIProjectClient` pour gérer un projet Foundry. Les anciens packages `Aspire.Azure.AI.OpenAI` et `Aspire.Azure.AI.Inference` ne sont plus publiés dans les nouvelles versions. Les applications qui les utilisent devront migrer vers les nouveaux packages et adapter leur code client.

## Kubernetes est stable, avec des prérequis à considérer

Les packages `Aspire.Hosting.Kubernetes` et `Aspire.Hosting.Azure.Kubernetes` sont maintenant stables. Le déploiement fondé sur Helm exige Helm 4.0.0 ou une version ultérieure. Les API de volumes persistants restent expérimentales. Aspire peut aussi cibler un cluster AKS existant, choisir le système d’exploitation des nœuds et configurer l’association de compte externe pour cert-manager.

Les nouveaux clusters AKS utilisent le niveau de contrôle Standard par défaut. Ce niveau comprend un SLA de disponibilité, mais il entraîne des frais. Aspire utilise aussi des identités gérées attribuées par l’utilisateur distinctes pour le plan de contrôle et le service kubelet. Lors du redéploiement d’un cluster existant, Azure peut mettre à jour les pools de nœuds. Les permissions accordées manuellement aux anciennes identités ne sont pas transférées. Il faut donc planifier ces changements et réattribuer les permissions requises.

## Les images par défaut et les changements incompatibles

Aspire 17 met à jour les images de conteneurs par défaut, dont MongoDB 9.0, PostgreSQL 18.6 et Redis 8.10. Le passage à MongoDB 9.0 est une mise à niveau majeure. Il faut vérifier la compatibilité des données persistées ou conserver explicitement l’ancienne version de l’image.

Voici quelques changements à examiner dans les projets existants :

- Les intégrations clientes RabbitMQ v6 et MongoDB v2 sont retirées. Aspire recommande les packages actuels avec RabbitMQ.Client 7.x et MongoDB.Driver 3.x.
- Le callback de configuration du client Azure Cosmos DB reçoit maintenant un `IServiceProvider` en plus des options.
- Le client OpenTelemetry passe de 128 Mio à 64 Mio comme taille maximale par défaut d’une requête OTLP. Les applications qui envoient de grands lots doivent vérifier cette limite.
- Les paramètres obligatoires refusent les chaînes vides. Un paramètre facultatif vide reste une chaîne vide, tandis qu’un paramètre facultatif non défini devient `null`.
- Les clusters AKS utilisent de nouvelles identités gérées, ce qui peut modifier les pools de nœuds lors d’un redéploiement.

La [documentation de mise à niveau d’Aspire 17](https://aspire.dev/whats-new/aspire-17/) contient la liste complète des changements et des migrations. Il est préférable de la consulter avant de mettre à jour les packages.

Pour mettre à jour le CLI, puis les packages Aspire du dépôt, la documentation indique les commandes suivantes :

```bash
aspire update --self
aspire update
```

## Conclusion

Aspire 17 réunit un tableau de bord centré sur les ressources, des outils CLI pour le travail d’équipe et de nouvelles fonctions de débogage dans Visual Studio Code. Les AppHost Go sont en aperçu. Les packages Kubernetes et plusieurs API sont maintenant stables.

Avant la mise à niveau, vérifiez le framework cible de l’AppHost, les anciennes API de projet, les packages clients retirés, les valeurs obligatoires et les images de conteneurs. Pour AKS, incluez dans cette revue le coût du niveau Standard, les nouvelles identités et les effets possibles sur les pools de nœuds.
